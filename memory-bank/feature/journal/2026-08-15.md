## Session : Correction critique — `apiFetch()` supprimait le corps de TOUTES les requêtes POST

### Symptôme rapporté par l'utilisatrice

Après avoir réglé N=5 ou N=10 dans le drawer de simulation (n'importe quel
circuit), la campagne lancée sortait systématiquement en N=10000, seed=42 —
config catalogue par défaut. Un premier correctif (garde de validation sur
`nIterations` dans `lancerCampagne()`, `CircuitPage.svelte` /
`solaire/+page.svelte`) n'a eu AUCUN effet observable — signe que le problème
n'était pas dans la valeur envoyée par le composant, mais plus loin dans la
chaîne réseau.

### Root cause réelle

**Fichier** : `frontend/src/lib/server/api.js`, fonction `apiFetch()`.

```js
// AVANT — bug
export async function apiFetch(path, init = {}) {
	const { json: body, headers, ...rest } = init;   // ← lit init.json, PAS init.body
	...
	body: body !== undefined ? JSON.stringify(body) : undefined,  // body est TOUJOURS undefined
	...
}
```

Le seul appelant réel, `api-proxy/[...path]/+server.js`, transmet le corps
sous la clé **`body`** (texte JSON brut déjà sérialisé côté client) :
```js
init.body = await request.text();
apiFetch(`/${path}`, init);
```

`apiFetch` ne regardait que `init.json` (jamais renseigné par cet appelant) →
`body` local valait toujours `undefined` → **le `fetch()` final partait sans
corps, pour CHAQUE POST/PUT/PATCH/DELETE passant par `/api-proxy/*`**, quel
que soit le circuit ou les paramètres réglés dans l'UI.

Côté backend, `POST /{circuit}/run` a un cas explicite pour un corps absent
(`req: CampagneRequest | None = None` → `if req is None: ... SimulationConfig
par défaut`), donc **aucune erreur** — la requête réussissait silencieusement
avec 100% de valeurs par défaut. C'est pour ça que TOUT (N_iterations, seed,
parametres_incertains) revenait toujours identique, pas seulement N.

### Correction

```js
// APRÈS — fix
export async function apiFetch(path, init = {}) {
	const { json, headers, body, ...rest } = init;   // body lu directement
	...
	const finalBody = json !== undefined ? JSON.stringify(json) : body;
	...
	body: finalBody,
	...
}
```

Garde le support du raccourci `json:` (objet JS à sérialiser) documenté dans
le JSDoc, tout en respectant `body:` (chaîne déjà sérialisée) — le seul cas
réellement utilisé aujourd'hui.

### Vérification

- Test direct backend (`curl` sur `127.0.0.1:4004`, hors navigateur) avec
  N=5 → confirmé respecté avant même le fix (preuve que le backend n'était
  jamais en cause).
- `npm run build` → succès.
- `pm2 restart app-simpy-liga-front`.
- Confirmé fonctionnel par l'utilisatrice après redéploiement (campagnes N=5
  respectées, temps de réponse normal).

### Fichiers modifiés
- `frontend/src/lib/server/api.js` — `apiFetch()`

### Pourquoi ce bug est resté invisible aussi longtemps
Il ne provoque **aucune erreur** — chaque requête aboutit en 200 OK avec un
résultat plausible (juste toujours le même, celui des valeurs par défaut).
Un bug qui répond "avec succès" mais avec le mauvais contenu est le plus
dangereux à diagnostiquer : rien ne le signale, seule la comparaison des
sorties le révèle.

### Piège à ne plus jamais reproduire (voir aussi `shared/systemPatterns.md`)
Toute fonction wrapper de `fetch()` qui accepte un corps de requête doit
lire la clé **exacte** utilisée par ses appelants réels. Ne jamais nommer un
paramètre de déstructuration différemment de la clé réellement passée sans
grep TOUS les appelants d'abord (`grep -rn "nomDeLaFonction(" src/`).
